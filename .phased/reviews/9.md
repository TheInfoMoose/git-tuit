## Independent pass

### Findings

**I1. Bare main repo blocks discard-checkout from a linked worktree** (new defect, medium)
- `asyncgit/src/sync/branch/mod.rs:535-550`, `check_branch_not_checked_out_elsewhere`.
- Trigger: bare repo + `git worktree add` layout (common). From a linked worktree, discard-checkout a local branch that the bare repo's `HEAD` names (e.g. `main`).
- Effect: refuses with "branch 'main' is checked out at <bare dir>". The main repo is opened via `commondir()` and its `HEAD` is compared with no `is_bare()` guard. Git skips bare worktrees when looking for a branch that's checked out elsewhere (from git source, not run here), so git allows this switch.
- Test gap that let it through: `t9b_linked_worktree_refuses` only covers main → linked. Nothing exercises the `repo.is_worktree()` branch at all, bare or not.

**I2. `cleanup_state` failure after `set_head` leaves a switched repo reported as failed** (new defect, low)
- `asyncgit/src/sync/branch/mod.rs:659-683` and the rollback at the end of `checkout_branch_discard`.
- Trigger: discard-checkout from Merge/Revert/CherryPick state to a remote target, and `repo.cleanup_state()` errors (permissions on `.git/MERGE_*`, for example).
- Effect: the worktree, index and HEAD have already moved to the new branch. The rollback then calls `new_branch.delete()` on the branch HEAD now points to. libgit2 refuses to delete the current HEAD branch and the error is swallowed by `let _`. The user sees an error, but the switch happened and MERGE_HEAD may remain. A local target hits the same error-after-switch report without the delete attempt. This path only exists because cleanup was added this phase.

**I3. A `git rm --cached` path whose content is unchanged now blocks discard-checkout** (new defect, low, over-refusal)
- `asyncgit/src/sync/branch/mod.rs:479-492`, `find_untracked_collisions`.
- Trigger: `git rm --cached foo` where `foo` on disk still equals HEAD, then discard-checkout to any branch.
- Effect: refused as a collision, even though nothing is at risk because the content is in HEAD. Discarding staged changes is the feature's purpose, and a staged deletion is one. The refusal is correct when the content differs (the `t9b_index_deleted_*` tests use edited content). It just doesn't compare against the HEAD blob. Safe direction, but the user has to unstage by hand first.

**I4. Abort removes a merge-added submodule dir with `remove_dir_all`** (new defect, low)
- `asyncgit/src/sync/merge.rs:147` (`0o160_000 => is_dir()` counts any dir as "matches index") plus `merge.rs:338` (`fs::remove_dir_all`).
- Trigger: a merge adds a gitlink, the user populates the submodule (`git submodule update --init`) before aborting.
- Effect: the whole submodule checkout, including its `.git` and any work in it, is deleted with no blocking check. `git reset --merge` leaves submodule directories in place. Rare, but it loses data that can't be recovered.

**I5. `t9b_upstream_failure_refuses` doesn't pin the failure source** (test defect, low)
- `src/popups/checkout_option.rs:864`: asserts only `res.is_err()`.
- If any earlier validation starts failing for this setup, the test still passes, and the "no leftover local branch" assertion becomes trivially true, so the branch rollback stops being tested. It should assert on the error text, or assert that it came from setting the upstream.

### Traced, no finding
- **Merge/revert abort (`merge.rs`)**: changed set = stage0 ≠ HEAD ∪ conflicted. Blocking = non-conflict changed paths whose worktree ≠ index, untracked content under dirs that need replacing, and non-dir ancestors of paths being restored. Then the order is worktree removals → path-limited checkout from HEAD → index `read_tree` → `cleanup_state`. This matches `git reset --merge` for the cases tested: untracked kept, unrelated edit kept, conflict restored, edited merge file refuses with nothing written, file↔dir both directions, revert. Content is compared by hash, not stat, so racy timestamps aren't an issue. Unborn HEAD clears the index.
- **Discard-checkout**: rebase/am states refuse before anything changes. Merge/revert/cherry-pick are cleaned up after the switch. The remote-target branch is now created *after* the collision check and *before* the checkout, so a `set_upstream` failure no longer leaves the worktree overwritten (launch checked out first). The linked-worktree scan skips self by canonical gitdir.
- **Push credentials (`cred.rs`, `push.rs`, `push_tags.rs`)**: the remote is resolved once in `start_push`, stored in `self.remote`, and `take()`n in `push_to_remote`. The credential-prompt path (`push.rs:423-431`) runs before `hide()`, so the remote is still set. `hide()` clears it. Credential lookup now uses the target remote's pushurl → url (it used the default push remote before), and the URL is checked for control characters (stricter than launch's `need_*`). push_tags resolves an empty remote to the default. App flows always pass `get_default_remote` for tags anyway (`app.rs:952-958`, `1262-1265`). Old helpers are still used by fetch and taglist, which is correct for fetch.
- **Force-push guard (`confirm.rs`)**: the local tip is captured when the confirm opens and compared on Enter. Error or missing branch → error message, no push. Covered by `t9d_moved_branch_refuses` (real key path, asserts origin unchanged) and `t9d_same_tip_pushes`. Note: this guards the *local* branch moving. It's not a remote lease (force-with-lease); see the contract pass for which was asked.
- **Strings/layout**: the new abort message is about 95 chars and goes through `wrapped_line_count` sizing. I didn't render it below 80 columns.
- **Sensitive data**: test URLs use `example.com`/`example.org` with placeholder users. No real hosts, emails or tokens.
