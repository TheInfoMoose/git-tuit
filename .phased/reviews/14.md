## Independent pass

### What changed (as read from code)
- `ThemePatchFile.base` now goes through `deserialize_optional_string` (`deserialize_any`): accepts `"x"`, `Some("x")`, `None`; anything else is a parse error.
- Base matching is trimmed and case-insensitive (`amber`, `classic`); unknown names warn and use classic.
- Base-less patch files log an `info!` hint telling the user to add `base: Some("amber")`.
- `OldThemeFile` gains `base: bool` (via `deserialize_present`). An old-format parse that saw a `base` key is now treated as an error: classic theme, file not rewritten.
- Docs: THEMES.md describes bare-string base, case-insensitivity, and "fails to parse → classic, file unchanged". CHANGELOG gains one line.

### Findings

**F1 — Mixed-form file with `base` loses every override (regression, low)**
- Where: `src/ui/style.rs:711-734` (the `Ok(old_theme) if !old_theme.base` guard and the `_ =>` arm).
- Trigger: a `theme.ron` with a `base` key plus any bare (non-`Some`) color, e.g. `(base: "amber", selection_bg: "Black")`. This is an easy mistake now that the docs say `base` takes a bare string; users will copy that style to the colors.
- Launch: `OldThemeFile` ignored the unknown `base` key, so the file loaded as classic + `selection_bg: Black` (then was rewritten, dropping `base`, which was destructive).
- Now: whole file rejected → plain classic, all overrides gone, only an `error!` that's invisible without `--logging`.
- Net: no longer destructive (good), but the user's colors silently vanish. `t14a_base_file_never_rewritten` case 1 locks this behavior in.
- Fix idea: if the old-format parse succeeds with `base` present, apply its colors on the named base in memory and still skip the rewrite.

**F2 — 14B hint is never asserted (test defect, low)**
- Where: `src/ui/style.rs:684-689` (message) vs `t14b_baseless_file_untouched` (`style.rs:1339+`).
- The test checks theme + file content only. Deleting the `log::info!` or changing its wording passes every test. The tests init a logger (`style.rs:792`) but nothing captures or asserts log output.
- Related, not a bug: the hint is `info!`, and logging only exists with `--logging` (`src/args.rs:49,148`). Most users will never see it. Flagging for the contract pass.

**F3 — CHANGELOG line describes a change no released user sees (new defect, docs, low)**
- Where: `CHANGELOG.md:18`.
- Says a base-less `theme.ron` "now fills unset fields from the classic colors instead of amber". At launch (`style.rs:613-615` base) base-less already used classic, and released gitui never had amber. The "instead of amber" is relative to an unreleased intermediate state.
- Meanwhile the real user-visible change (amber is the default on truecolor terminals with no `theme.ron`) has no CHANGELOG entry at launch or now (`grep amber CHANGELOG.md --base`: no hits).
